# NVIDIA 통합 SPK 자동 전달·설치 설계

상태: 자동 전달·설치 코드 반영 완료, 공개 애드온 배포와 DSM 실기 파일럿 검증 전

범위: `tcrp-addons/nvidiadriver`의 버전 선택과 통합 드라이버·필수 GPU Monitor·선택 컨테이너 런타임/FFmpeg SPK 전달

목표: 사용자가 선택한 **실제로 게시된** 버전의 드라이버 SPK와 필수 Monitor SPK, 선택한 경우 컨테이너 런타임/FFmpeg SPK를 안전하게 내려받아 DSM에서 설치한다. 595 계열까지 고려하되, 없는 빌드를 있는 것처럼 표시하지 않는다.

## 결론

현재의 “junior `on_patches`에서 내려받아 `/tmp`에 두고 `on_os_load`에서 `/tmpRoot`에 주입”하는 방법은 작은 모듈 계층에는 맞지만, 900 MB를 넘는 통합 SPK에는 재사용하지 않는다. 기존 버전 선택·GPU 적합성 판단만 재활용하고, **부트 로더에는 작은 고정 매니페스트와 선택 결과만 넣는다.** DSM 부팅 후 데이터 볼륨과 패키지 서비스가 준비되면 일회성 작업자가 영구 볼륨에 각 SPK를 내려받아 검증하고 DSM 패키지 관리자로 설치한다. 이 작업이 실패해도 DSM 부팅을 막지 않는다.

SPK와 기존 계층 주입은 동일 드라이버에 대해 **상호 배타적**이어야 한다. SPK 경로를 선택했다면 기존 `nv-ko`/userspace/GSP 주입 및 기존 NVIDIA 부트 훅이 같은 파일을 다시 덮지 않게 해야 한다. GSP는 필요한 통합 드라이버 SPK 내부에 이미 포함되므로 새 SPK 전달 경로에서는 **별도 GSP 다운로드·설치 항목을 만들지 않는다.** 기존 설치에서 전환하는 절차는 파일 소유권·충돌 검사 후 별도로 검증한다.

## 기존 계층 주입 방식과 제약

기존 경로(`nvidia_spk_delivery=false`)는 `on_patches`에서 `/tmp/nvdriver`에 계층을 다운로드하고 `on_os_load`에서 `/tmpRoot`에 추출한다. `/tmp/nvdriver`는 junior의 임시 메모리 공간이며 기존 `fetch()`는 `curl -k`를 쓰고 해시 도구가 없으면 검증을 건너뛴다. 이 경로는 대용량 SPK에 사용하지 않는다. 신규 기본 SPK 경로는 동일 훅에서 작은 선택 계획만 준비하고 DSM 부팅 후 작업자가 실행된다. `recipes/universal.json`은 두 훅을 등록하고, 로더의 `/addons/nvidia.conf`가 사용자 선택을 전달한다.

통합 SPK는 플랫폼별 `.tgz`를 다시 조립하는 대상이 아니라 **이미 패키징된 단일 파일**이다. SPK를 initrd 또는 `/tmpRoot`에 넣으면 부트 이미지/메모리/시스템 파티션을 불필요하게 압박한다. 또한 junior 시점에는 패키지 서비스와 데이터 볼륨의 준비를 보장할 수 없으므로 그 자리에서 `synopkg install`을 실행하지 않는다.

현재 게시·빌드되는 조합(설계 시점)은 아래와 같다. 게시 자산의 존재, 정확한 이름, 크기, SHA-256은 **배포 매니페스트 생성 시 다시 확인**한다.

| 패키지 변형 | 커널·DSM 범위 | 현재 SPK 드라이버 버전 | 패키지 ID |
|---|---|---|---|
| kver5 | 5.10.55, DSM 7.2 이상 | 580.173.02, 595.99.02 | `syno-nvidia-driver-kver5` |
| kver4-72 | 4.4.302, DSM 7.2–7.4 | 550.163.01 | `syno-nvidia-driver-kver4-dsm72` |
| kver4-70 | 4.4.180, DSM 7.0–7.1 | 550.163.01 | `syno-nvidia-driver-kver4-dsm70` |

현 `scripts/build-spk.sh`의 분기 기준이다. K5 535/550 및 K4 580/595 SPK는 현재 분기에서 만들지 않으므로 기존 계층 인덱스에 버전이 있다는 이유만으로 SPK 설치 메뉴에 노출하면 안 된다. 595 지원 범위는 **GPU PCI ID/드라이버 호환성·GSP 요구사항**과 게시된 SPK 자산을 함께 통과해야 한다. `arch`가 여러 플랫폼을 나열하더라도 실제 커널 ABI가 동일하다는 뜻은 아니며, 통합 SPK 안의 정확한 플랫폼 모듈을 설치 스크립트가 고르는지 검증한다.

## 설치 구성과 의존 관계

| 구성 요소 | 선택 조건 | 현재 게시 예시 | 패키지 ID·설치 원칙 |
|---|---|---|---|
| 통합 NVIDIA 드라이버 | 사용자가 드라이버 버전을 선택 | 위 표의 커널별 SPK | 항상 먼저 설치. 플랫폼·GPU 호환성을 검사한다. |
| NVIDIA GPU Monitor | **드라이버 SPK 설치 시 필수** | `syno-nvidia-gpu-monitor-0.6.5-x86_64.spk` | `syno-nvidia-gpu-monitor`. 드라이버 뒤에 설치. 사용자가 끄는 선택지는 두지 않는다. 이미 정확한 버전이면 건너뛴다. |
| NVIDIA Container Runtime | 사용자가 로더에서 선택한 경우만 | `syno-nvidia-container-runtime-1.19.1-3-x86_64.spk` | `syno-nvidia-container-runtime`. 드라이버 활성 확인 후 설치. 선택하지 않았다면 새로 설치하지 않으며 기존 설치도 자동 제거하지 않는다. |
| NVIDIA FFmpeg | 사용자가 로더에서 선택하고 **해당 드라이버용 SPK가 게시·검증된 경우만** | 550.163.01 / 580.173.02 / 595.99.02 | 독립 `syno-nvidia-ffmpeg` SPK. 드라이버 활성 확인 후 설치하며 Jellyfin 연동은 별도 상태로 검증한다. 595용 FFmpeg 8.1 자동 Jellyfin 전환은 서버 12 이상에서만 허용한다. |

Monitor와 컨테이너 런타임은 드라이버 버전과 **독립적인 SPK 버전**을 가진다. FFmpeg는 검증된 드라이버 호환 범위를 명시한다. 각 SPK의 정확한 자산명·크기·SHA-256·`INFO`를 따로 고정한다. 현재 예시 버전은 배포 시점에 다시 검증한다. GSP는 드라이버 SPK의 내부 구성 요소이며 별도 설치 단계가 아니다. FFmpeg 패키지의 소유권·Jellyfin 연동·595 지원 공백은 `syno_nvidia_driver/docs/nvidia-ffmpeg-spk-design.md`에 상세히 둔다.

드라이버와 필수 Monitor의 **다운로드·검증이 모두 끝나야** 첫 설치를 시작한다. Monitor의 사전 검증이 실패하면 드라이버도 설치하지 않는다. 설치 단계의 Monitor 실패는 드라이버가 설치된 뒤일 수 있으므로 전체 작업을 완료로 표시하지 않는다(`monitor_failed`/재시도 대기). 드라이버를 자동 제거하거나 되돌리지 않고, 검증된 Monitor SPK와 오류 로그를 보존한다. 선택 런타임의 실패는 드라이버·Monitor의 성공을 취소하지 않지만 `runtime_failed`라는 미완료 선택 기능으로 표시한다. 어느 경우에도 재부팅 때 무한 설치 루프를 만들지 않는다.

## 권장 흐름

1. 로더 메뉴는 플랫폼, DSM 빌드, `uname -r`에 해당하는 커널 계열, GPU PCI ID를 식별하고, SPK 매니페스트와 GPU 호환성 카탈로그의 **교집합**만 선택지로 표시한다. 자동 선택도 같은 규칙을 따른다. 선택한 드라이버 버전과 컨테이너 런타임/FFmpeg 선택 여부, 매니페스트 항목의 고유 ID를 `/addons/nvidia.conf` 같은 작은 설정으로 고정한다. Monitor는 항상 포함하며 GSP 선택지는 없다. FFmpeg는 해당 드라이버와 호환·게시된 SPK가 없으면 설치 가능 선택지로 표시하지 않는다.
2. junior 훅은 SPK를 다운로드하거나 설치하지 않는다. 검증된 소형 매니페스트, 선택 정보, DSM용 일회성 시작 스크립트만 준비한다. 기존 `on_os_load` 방식으로 작은 파일을 배치할 수는 있지만, DSM 시작 훅의 정확한 실행 시점과 지속성은 실기에서 확인한 뒤 확정한다.
3. DSM이 완전히 기동한 뒤 작업자는 네트워크, 지정 데이터 볼륨, 패키지 서비스가 준비될 때까지 **부팅을 막지 않고** 제한 시간·백오프로 기다린다. 지정 볼륨이 없다면 다른 파티션으로 자동 우회하지 않고 `waiting_for_volume`을 기록한다.
4. 영구 데이터 볼륨의 root 전용 디렉터리(예: 선택한 볼륨의 `@appdata/nvidia-driver-installer`)에 필요한 **각 SPK를 개별** `.part`로 내려받는다. 완료 후 길이와 SHA-256을 확인하고 동일 파일시스템에서 원자적으로 최종 이름으로 바꾼다. TLS 인증을 켜고 HTTPS 리다이렉트를 허용하되, 허용된 게시자/호스트와 매니페스트의 고정 자산만 받는다. 실패·중단 시 제한된 재시도와 resume을 사용하며 **resume 후에도 전체 해시를 다시 검증**한다.
5. 각 SPK를 새로 설치했거나 이미 정확한 버전·페이로드로 설치된 경우 모두 `synopkg start <package>`를 시도한다. NVIDIA 드라이버는 명령의 종료코드만 성공 기준으로 삼지 않는다. 최대 8회 시작을 시도하며 매회 기대 버전의 `nvidia` 모듈, `/proc/modules`, `/dev/nvidiactl`, 번호가 붙은 `/dev/nvidiaN` 문자 장치를 확인하고, 장치가 준비되지 않았으면 10초 뒤 재시도한다. 다른 NVIDIA 모듈 버전이 이미 로드되어 있으면 반복하지 않고 재부팅 필요 상태로 넘긴다. SPK의 `startable="no"` 설정은 Package Center의 Start/Stop UI 버튼 노출을 제어하므로, `synopkg start`를 호출해도 UI 버튼이 생기는 것은 아니다.
6. 충분한 공간을 다시 확인하고, 각 SPK의 `INFO` 메타데이터(`package`, `version`, `arch`, `os_min_ver`, `extractsize`)와 역할별 매니페스트 항목을 대조한다. `INFO`를 쉘 스크립트로 `source`하지 않는다. 압축 경로·형식도 검사한다. 불일치하면 해당 SPK를 설치하지 않는다.
7. 역할별로 설치된 패키지 ID/버전을 조회한다. 정확히 같으면 재설치하지 않는다. 명시적으로 선택된 상위 드라이버 버전만 기존 패키지의 정상 업그레이드 경로로 진행한다. 하위 버전 전환이나 다른 변형 패키지로의 전환은 별도 승인/마이그레이션 절차로 분리하고 자동 삭제하지 않는다.
8. DSM 패키지 관리자가 허용하는 방식으로 검증된 로컬 SPK를 **드라이버 → 필수 Monitor** 순으로 설치한다. 후보 명령은 `synopkg install <검증된 경로>`이지만, 정확한 DSM 7.4 동작·권한·경고 처리 방식은 실기 파일럿에서 확정한다. CLI가 UI보다 설치 제한을 우회한다고 가정하지 않는다. 실패 시 검증된 SPK를 보존하고 경로와 DSM 패키지 로그를 알려 사용자가 패키지 센터에서 수동 설치할 수 있게 한다.
9. 설치 성공과 GPU 활성은 다른 상태다. 패키지 서비스를 호출할 수 있게 된 직후에도 DSM의 패키지 시작/종료 작업이 진행 중일 수 있으므로, 작업자는 설치 전에 30초 안정화 대기를 한다. `synopkg install`이 알려진 전환 오류(code 263)를 반환하면 15초 간격으로 최대 8회 재시도하고, 그 밖의 오류는 실패로 남긴다. 다른 버전의 NVIDIA 모듈이 이미 로드되어 있다면 즉시 교체를 강행하지 않고 `installed_pending_reboot`로 기록해 재부팅을 안내한다. 모듈이 아직 없거나 선택 버전은 맞지만 장치 노드가 준비되지 않은 경우에는 백그라운드 작업자가 제한 시간 동안 기다린 뒤, 같은 검증된 드라이버 SPK를 **번들당 한 번만** 지연 재설치하고 다시 확인한다. 끝내 모듈·`/dev/nvidiactl`·GPU 장치 노드가 확인되지 않으면 완료로 표시하지 않는다. 컨테이너 런타임/FFmpeg가 선택되었다면 이 **활성 확인 후** 각각 별도 SPK를 설치하고 Docker/Jellyfin 연동을 검증한다. Monitor는 드라이버와 함께 필수 설치 상태여야 작업을 완료로 표시한다.

## 매니페스트 계약

매니페스트는 로더와 함께 버전 고정되어야 한다. 원격의 가변 `latest`나 해시 없는 URL을 부팅 때 그대로 신뢰하지 않는다. 자산을 새로 게시할 때 빌드/릴리즈 파이프라인이 자산의 실제 byte 수와 SHA-256을 산출하고, 다음 로더/애드온 업데이트에 반영한다. GitHub Release의 태그 URL 자체는 교체 가능하므로 **해시가 최종 신뢰 기준**이다. 아래는 드라이버 항목 예시이고, Monitor와 런타임에도 같은 자산 필드를 가진 독립 항목이 필요하다:

```json
{
  "variant": "kver5",
  "kernel": "5.10.55",
  "dsm_min": "7.2",
  "platforms": ["epyc7002", "epyc7003"],
  "driver_version": "595.99.02",
  "package_id": "syno-nvidia-driver-kver5",
  "package_version": "595.99.02-3",
  "asset_url": "https://github.com/PeterSuh-Q3/syno_nvidia_driver/releases/download/spk/<exact-asset>.spk",
  "size_bytes": "<actual integer>",
  "sha256": "<actual 64-hex digest>",
  "extractsize_kb": "<actual INFO value>"
}
```

번들 선택 항목은 `driver` 자산 ID, 필수 `monitor` 자산 ID, 선택적 `container_runtime`/`ffmpeg` 자산 ID와 선택 여부를 함께 기록한다. `gsp` 자산 ID는 두지 않는다. 위 JSON은 **스키마 예시**이며 배포 가능한 실제 매니페스트가 아니다. 플랫폼 전체 목록·DSM 최대 버전·GPU 지원 정보도 실자산과 일치해야 한다. 각 `package_version`은 해당 SPK의 DSM `INFO`와 같아야 한다. 매니페스트 생성 단계에서 다운로드한 모든 SPK의 `INFO` 및 릴리즈 자산 크기/해시를 비교하고, 값이 빠진 항목은 빌드를 실패시킨다. SHA-256 도구가 없는 환경에서 검증을 생략하지 않는다.

## 공간·중단·보안 정책

- **데이터 볼륨과 DSM 임시 공간을 각각 검사:** 선택된 모든 SPK의 총 크기 `ΣS`와 설치 시점의 최대 추출 크기 `Emax`를 고려한다. DSM 설치기가 별도의 임시 복사/추출을 하는지 실기에서 측정해야 한다. 그 전에는 추가 여유를 보수적으로 `2 × ΣS + Emax + 1 GiB` 이상으로 계획하고, 대상 볼륨 및 DSM 임시/시스템 공간을 별도로 확인한다. 이는 최종 보증치가 아닌 파일럿 전 안전 기준이다. 부족하면 다운로드·설치를 시작하지 않는다.
- **원자성과 멱등성:** 상태 파일은 원자적 교체, 작업은 단일 잠금으로 보호한다. 역할별 다운로드·검증·설치 상태와 전체 번들 상태를 별도로 저장한다. `selected → waiting → downloading → verified → driver_installed → monitor_installed → installed_pending_reboot → driver_active → runtime_installed(선택 시) → active`와 역할별 `failed`를 구분한다. 재부팅 뒤 `verified` 파일은 재검증해 재사용하고, 설치 중단 시 각 패키지의 실제 상태부터 재조회한다. 무한 자동 설치 루프를 금지한다.
- **무결성:** 인증서 검증을 끄는 `curl -k`를 금지하고, HTTP 오류를 실패 처리한다. 정확한 길이와 SHA-256, SPK 메타데이터 모두 통과해야 설치한다. 체크섬 도구/네트워크/시간 동기화가 없으면 실패를 명시하고 닫힌 상태로 둔다.
- **최소 권한·경로:** 작업자와 캐시는 root 소유, 디렉터리는 0700. 허용된 절대경로만 사용하고 심볼릭 링크/경로 치환을 검사한다. 선택 문자열을 쉘 명령에 직접 삽입하거나 원격 스크립트를 실행하지 않는다. 토큰·개인 URL은 로그에 남기지 않는다.
- **보존/정리:** 성공을 확인하기 전까지 마지막 검증된 SPK와 실패 로그를 보존한다. 새 버전 활성화 후 오래된 캐시만 크기·버전 정책에 따라 정리한다. 설치 실패만으로 기존 패키지나 모듈을 삭제하지 않는다.

## 파일럿과 수용 기준

1. 로더에서 각 변형의 실제 게시 버전만 표시하고, 비호환 GPU/커널/DSM을 거부한다. 특히 K5 595와 K4 550을 별도로 시험한다. GSP를 별도로 다운로드·설치하지 않고 필요한 드라이버 SPK에 내장됐는지 확인한다.
2. 900 MB 이상 드라이버 파일과 추가 SPK들에 대해 성공, 끊김 후 재개, 길이 불일치, 해시 불일치, HTTP 오류, 인증서 오류, 공간 부족, 볼륨 지연을 시험한다. 실패 시 부팅은 정상 진행되고 검증 실패한 파일의 설치는 일어나지 않아야 한다.
3. DSM 패키지 서비스 준비 전/후, `synopkg` CLI의 반환·로그·경고, 수동 설치 폴백을 실기에서 확인한다. Synology의 제3자 패키지 경고/호환성 제한을 우회하지 않는다.
4. 같은 버전 재부팅은 무동작, 상위 버전 선택은 정상 업그레이드, 중단 후 재부팅은 안전한 재조회, 설치 후 재부팅 요구는 명확한 상태로 검증한다.
5. 기존 로더 주입 방식과 SPK가 동시에 활성화되지 않도록 전환 검사를 통과한다. 드라이버 설치 후 Monitor 필수 설치·동일 버전 재부팅 무동작·Monitor 설치 실패 후 안전한 재시도를 검증한다. 컨테이너 런타임을 선택한 경우에만 활성 드라이버 확인 후 런타임 SPK 설치·Docker GPU 사용을 시험한다. 선택하지 않은 경우 새 런타임 설치가 없어야 한다.

## 현재 구현 상태와 남은 검증

1. 게시된 드라이버·Monitor·컨테이너 런타임·FFmpeg SPK의 크기/SHA-256/INFO를 포함한 고정 매니페스트를 `src/nvidia-spk-index.json`으로 추가했다. recipe의 파일 해시도 실제 값으로 고정한다. GSP는 별도 항목이 아니다.
2. 기본 경로를 SPK 전달로 전환하고 기존 TGZ 주입과 상호 배타적으로 분기했다. `nvidia_spk_delivery=false`일 때에만 기존 경로를 유지한다. Monitor는 필수, 컨테이너 런타임과 FFmpeg는 사용자 선택이다.
3. DSM용 일회성 작업자 `src/spk-install.sh`를 추가했다. 영구 볼륨에 다운로드하고, SHA-256/크기/SPK INFO를 확인한 뒤 드라이버 → 필수 Monitor 순서로 설치한다. 런타임/FFmpeg는 드라이버 모듈 활성 확인 후 설치한다. 상태 파일·로그·공간 부족 대기·제한 재시도·드라이버 변형 충돌 거부를 구현했다.
4. SPK 작업자는 선택 자산 SHA-256과 설치 payload 해시를 완료 상태에 함께 고정하고, 완료 표식이 있어도 번들 지문·설치 payload·드라이버 장치 활성 상태를 재검증한다. 설치 전에 30초 패키지 서비스 안정화 대기를 하고, `synopkg` code 263 전환 오류는 최대 8회 제한 재시도한다. 최초 활성 확인이 지연되면 제한된 대기 후 번들당 한 번만 드라이버 재설치를 시도한다. 아직 공개 저장소로 배포하거나 NAS 실기에서 자동 실행·업그레이드·재부팅·복구를 검증하지 않았다. 공개 애드온을 갱신하기 전 recipe 해시가 원격 커밋 내용과 일치하는지 확인하고, 이후 먼저 다운로드/검증 전용 및 한 변형 파일럿을 거친다. 실패 시 DSM 정상 패키지 절차를 사용하고 임의 모듈 교체는 하지 않는다.
