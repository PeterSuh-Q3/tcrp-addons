# NVIDIA 통합 SPK 자동 전달·설치 설계

상태: 설계안 (구현 전)

범위: `tcrp-addons/nvidiadriver`의 버전 선택과 `syno_nvidia_driver` 통합 드라이버 SPK 전달

목표: 사용자가 선택한 **실제로 게시된** 버전의 SPK를 안전하게 내려받아 DSM에서 설치한다. 595 계열까지 고려하되, 없는 빌드를 있는 것처럼 표시하지 않는다.

## 결론

현재의 “junior `on_patches`에서 내려받아 `/tmp`에 두고 `on_os_load`에서 `/tmpRoot`에 주입”하는 방법은 작은 모듈 계층에는 맞지만, 900 MB를 넘는 통합 SPK에는 재사용하지 않는다. 기존 버전 선택·GPU 적합성 판단만 재활용하고, **부트 로더에는 작은 고정 매니페스트와 선택 결과만 넣는다.** DSM 부팅 후 데이터 볼륨과 패키지 서비스가 준비되면 일회성 작업자가 영구 볼륨에 SPK를 내려받아 검증하고 DSM 패키지 관리자로 설치한다. 이 작업이 실패해도 DSM 부팅을 막지 않는다.

SPK와 기존 계층 주입은 동일 드라이버에 대해 **상호 배타적**이어야 한다. SPK 경로를 선택했다면 기존 `nv-ko`/userspace/GSP 주입 및 기존 NVIDIA 부트 훅이 같은 파일을 다시 덮지 않게 해야 한다. 기존 설치에서 전환하는 절차는 파일 소유권·충돌 검사 후 별도로 검증한다.

## 현재 방식과 제약

`src/install.sh`는 `on_patches`에서 `/tmp/nvdriver`에 계층을 다운로드하고, `on_os_load`에서 `/tmpRoot`에 추출한다. `/tmp/nvdriver`는 junior의 임시 메모리 공간이다. 현 `fetch()`는 `curl -k`를 사용하며 해시 도구가 없으면 검증을 건너뛴다. 두 동작 모두 대용량 SPK 전달 경로에 가져오지 않는다. `recipes/universal.json`은 이 두 훅을 등록하고, 로더의 `/addons/nvidia.conf`가 사용자 선택을 전달한다.

통합 SPK는 플랫폼별 `.tgz`를 다시 조립하는 대상이 아니라 **이미 패키징된 단일 파일**이다. SPK를 initrd 또는 `/tmpRoot`에 넣으면 부트 이미지/메모리/시스템 파티션을 불필요하게 압박한다. 또한 junior 시점에는 패키지 서비스와 데이터 볼륨의 준비를 보장할 수 없으므로 그 자리에서 `synopkg install`을 실행하지 않는다.

현재 게시·빌드되는 조합(설계 시점)은 아래와 같다. 게시 자산의 존재, 정확한 이름, 크기, SHA-256은 **배포 매니페스트 생성 시 다시 확인**한다.

| 패키지 변형 | 커널·DSM 범위 | 현재 SPK 드라이버 버전 | 패키지 ID |
|---|---|---|---|
| kver5 | 5.10.55, DSM 7.2 이상 | 580.173.02, 595.99.02 | `syno-nvidia-driver-kver5` |
| kver4-72 | 4.4.302, DSM 7.2–7.4 | 550.163.01 | `syno-nvidia-driver-kver4-dsm72` |
| kver4-70 | 4.4.180, DSM 7.0–7.1 | 550.163.01 | `syno-nvidia-driver-kver4-dsm70` |

현 `scripts/build-spk.sh`의 분기 기준이다. K5 535/550 및 K4 580/595 SPK는 현재 분기에서 만들지 않으므로 기존 계층 인덱스에 버전이 있다는 이유만으로 SPK 설치 메뉴에 노출하면 안 된다. 595 지원 범위는 **GPU PCI ID/드라이버 호환성·GSP 요구사항**과 게시된 SPK 자산을 함께 통과해야 한다. `arch`가 여러 플랫폼을 나열하더라도 실제 커널 ABI가 동일하다는 뜻은 아니며, 통합 SPK 안의 정확한 플랫폼 모듈을 설치 스크립트가 고르는지 검증한다.

## 권장 흐름

1. 로더 메뉴는 플랫폼, DSM 빌드, `uname -r`에 해당하는 커널 계열, GPU PCI ID를 식별하고, SPK 매니페스트와 GPU 호환성 카탈로그의 **교집합**만 선택지로 표시한다. 자동 선택도 같은 규칙을 따른다. 선택한 드라이버 버전과 매니페스트 항목의 고유 ID를 `/addons/nvidia.conf` 같은 작은 설정으로 고정한다.
2. junior 훅은 SPK를 다운로드하거나 설치하지 않는다. 검증된 소형 매니페스트, 선택 정보, DSM용 일회성 시작 스크립트만 준비한다. 기존 `on_os_load` 방식으로 작은 파일을 배치할 수는 있지만, DSM 시작 훅의 정확한 실행 시점과 지속성은 실기에서 확인한 뒤 확정한다.
3. DSM이 완전히 기동한 뒤 작업자는 네트워크, 지정 데이터 볼륨, 패키지 서비스가 준비될 때까지 **부팅을 막지 않고** 제한 시간·백오프로 기다린다. 지정 볼륨이 없다면 다른 파티션으로 자동 우회하지 않고 `waiting_for_volume`을 기록한다.
4. 영구 데이터 볼륨의 root 전용 디렉터리(예: 선택한 볼륨의 `@appdata/nvidia-driver-installer`)에 `.part`로 내려받는다. 완료 후 길이와 SHA-256을 확인하고 동일 파일시스템에서 원자적으로 최종 이름으로 바꾼다. TLS 인증을 켜고 HTTPS 리다이렉트를 허용하되, 허용된 게시자/호스트와 매니페스트의 고정 자산만 받는다. 실패·중단 시 제한된 재시도와 resume을 사용하며 **resume 후에도 전체 해시를 다시 검증**한다.
5. 충분한 공간을 다시 확인하고, SPK의 `INFO` 메타데이터(`package`, `version`, `arch`, `os_min_ver`, `extractsize`)와 선택 항목을 대조한다. `INFO`를 쉘 스크립트로 `source`하지 않는다. 압축 경로·형식도 검사한다. 불일치하면 설치하지 않는다.
6. 설치된 패키지 ID/버전을 조회한다. 정확히 같으면 재설치하지 않는다. 명시적으로 선택된 상위 버전만 기존 패키지의 정상 업그레이드 경로로 진행한다. 하위 버전 전환이나 다른 변형 패키지로의 전환은 별도 승인/마이그레이션 절차로 분리하고 자동 삭제하지 않는다.
7. DSM 패키지 관리자가 허용하는 방식으로 검증된 로컬 SPK를 설치한다. 후보 명령은 `synopkg install <검증된 경로>`이지만, 정확한 DSM 7.4 동작·권한·경고 처리 방식은 실기 파일럿에서 확정한다. CLI가 UI보다 설치 제한을 우회한다고 가정하지 않는다. 실패 시 검증된 SPK를 보존하고 경로와 DSM 패키지 로그를 알려 사용자가 패키지 센터에서 수동 설치할 수 있게 한다.
8. 설치 성공과 GPU 활성은 다른 상태다. 기존 NVIDIA 모듈이 로드되어 있다면 즉시 교체를 강행하지 않고 `installed_pending_reboot`로 기록해 재부팅을 안내한다. 재부팅 후 버전 일치, `nvidia-smi`, 모듈 상태를 확인한 뒤 `active`로 완료한다.

## 매니페스트 계약

매니페스트는 로더와 함께 버전 고정되어야 한다. 원격의 가변 `latest`나 해시 없는 URL을 부팅 때 그대로 신뢰하지 않는다. 자산을 새로 게시할 때 빌드/릴리즈 파이프라인이 자산의 실제 byte 수와 SHA-256을 산출하고, 다음 로더/애드온 업데이트에 반영한다. GitHub Release의 태그 URL 자체는 교체 가능하므로 **해시가 최종 신뢰 기준**이다. 매니페스트 항목의 최소 필드:

```json
{
  "variant": "kver5",
  "kernel": "5.10.55",
  "dsm_min": "7.2",
  "platforms": ["epyc7002", "epyc7003"],
  "driver_version": "595.99.02",
  "package_id": "syno-nvidia-driver-kver5",
  "package_version": "595.99.02-3",
  "asset_url": "https://github.com/PeterSuh-Q3/syno_nvidia_driver/releases/download/spk/<exact-asset>.spk",
  "size_bytes": "<actual integer>",
  "sha256": "<actual 64-hex digest>",
  "extractsize_kb": "<actual INFO value>"
}
```

위 JSON은 **스키마 예시**이며 배포 가능한 실제 매니페스트가 아니다. 플랫폼 전체 목록·DSM 최대 버전·GPU 지원 정보도 실자산과 일치해야 한다. `package_version`은 DSM `INFO`와 같아야 한다. 매니페스트 생성 단계에서 다운로드한 SPK의 `INFO` 및 릴리즈 자산 크기/해시를 비교하고, 값이 빠진 항목은 빌드를 실패시킨다. SHA-256 도구가 없는 환경에서 검증을 생략하지 않는다.

## 공간·중단·보안 정책

- **데이터 볼륨과 DSM 임시 공간을 각각 검사:** 다운로드 볼륨에는 SPK 크기 `S`와 재시도·임시 파일 여유가 필요하다. DSM 설치기가 별도의 임시 복사/추출을 하는지 실기에서 측정해야 한다. 그 전에는 추가 여유를 보수적으로 `2 × S + INFO.extractsize + 1 GiB` 이상으로 계획하고, 대상 볼륨 및 DSM 임시/시스템 공간을 별도로 확인한다. 이는 최종 보증치가 아닌 파일럿 전 안전 기준이다. 부족하면 다운로드·설치를 시작하지 않는다.
- **원자성과 멱등성:** 상태 파일은 원자적 교체, 작업은 단일 잠금으로 보호한다. `selected → waiting → downloading → verified → installing → installed_pending_reboot → active`와 `failed`를 구분한다. 재부팅 뒤 `verified` 파일은 재검증해 재사용하고, `installing`은 실제 설치 상태부터 재조회한다. 무한 자동 설치 루프를 금지한다.
- **무결성:** 인증서 검증을 끄는 `curl -k`를 금지하고, HTTP 오류를 실패 처리한다. 정확한 길이와 SHA-256, SPK 메타데이터 모두 통과해야 설치한다. 체크섬 도구/네트워크/시간 동기화가 없으면 실패를 명시하고 닫힌 상태로 둔다.
- **최소 권한·경로:** 작업자와 캐시는 root 소유, 디렉터리는 0700. 허용된 절대경로만 사용하고 심볼릭 링크/경로 치환을 검사한다. 선택 문자열을 쉘 명령에 직접 삽입하거나 원격 스크립트를 실행하지 않는다. 토큰·개인 URL은 로그에 남기지 않는다.
- **보존/정리:** 성공을 확인하기 전까지 마지막 검증된 SPK와 실패 로그를 보존한다. 새 버전 활성화 후 오래된 캐시만 크기·버전 정책에 따라 정리한다. 설치 실패만으로 기존 패키지나 모듈을 삭제하지 않는다.

## 파일럿과 수용 기준

1. 로더에서 각 변형의 실제 게시 버전만 표시하고, 비호환 GPU/커널/DSM을 거부한다. 특히 K5 595와 K4 550을 별도로 시험한다.
2. 900 MB 이상 파일에 대해 성공, 끊김 후 재개, 길이 불일치, 해시 불일치, HTTP 오류, 인증서 오류, 공간 부족, 볼륨 지연을 시험한다. 실패 시 부팅은 정상 진행되고 설치는 일어나지 않아야 한다.
3. DSM 패키지 서비스 준비 전/후, `synopkg` CLI의 반환·로그·경고, 수동 설치 폴백을 실기에서 확인한다. Synology의 제3자 패키지 경고/호환성 제한을 우회하지 않는다.
4. 같은 버전 재부팅은 무동작, 상위 버전 선택은 정상 업그레이드, 중단 후 재부팅은 안전한 재조회, 설치 후 재부팅 요구는 명확한 상태로 검증한다.
5. 기존 로더 주입 방식과 SPK가 동시에 활성화되지 않도록 전환 검사를 통과한다. 실제 GPU에서 모듈 버전, `nvidia-smi`, 컨테이너 런타임(해당하는 경우)을 별개로 점검한다.

## 구현 순서

1. 게시된 SPK 기반 매니페스트 생성기와 자산 검증 CI를 만든다.
2. 버전 선택을 SPK 가용성·GPU 호환성 교집합으로 전환하고 기존 주입과 배타적으로 한다.
3. DSM 일회성 다운로더/설치기 및 상태·로그를 구현한다. 먼저 **다운로드/검증 전용 모드**로 실기에서 공간·부팅 시점을 측정한다.
4. 한 변형/한 버전에서 설치를 검증한 뒤 K5 580/595, K4 550 순으로 확장한다. 실패 후 롤백은 DSM 정상 패키지 절차로 설계하고 임의 모듈 교체는 하지 않는다.

## 근거 자료

- [Synology DSM 7 패키지/CLI 변경사항](https://help.synology.com/developer-guide/breaking_changes.html): `synopkg install`은 UI 설치와 동일한 제약을 적용하며, 제3자 패키지 경고가 있다.
- [Synology INFO optional fields](https://help.synology.com/developer-guide/synology_package/INFO_optional_fields.html): `extractsize`는 설치 공간 판단에 쓰는 필드다.
- [Synology package.tgz 배치](https://help.synology.com/developer-guide/synology_package/package_tgz/package_tgz.html): 패키지 본체는 설치 대상 볼륨/시스템 위치에 배치된다.
